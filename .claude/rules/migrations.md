# Database migration rules

- Schema changes ship as a new Alembic revision; never edit an applied revision (0001 is the baseline).
- Generate with `alembic revision --autogenerate -m "..."` against a scratch SQLite DB, then **review by hand**:
  - replace `app.core.db.UTCDateTime` with `sa.DateTime(timezone=True)` (migrations must not import app code);
  - expression indexes (e.g. `lower(name)`) are not autogenerated — add them explicitly;
  - data migrations must be idempotent and batched.
- Keep migrations portable (SQLite for tests, PostgreSQL 16 in production). If PostgreSQL-only DDL is unavoidable,
  guard it with `op.get_bind().dialect.name == "postgresql"` and note the limitation in `docs/03-DATABASE-SCHEMA.md`.
- Every migration must pass `bash scripts/test/run.sh migrations` (upgrade, `alembic check`, downgrade, upgrade).
- New tables need: primary key, foreign keys with deliberate ON DELETE behaviour, indexes for each filter/sort column,
  unique constraints that enforce business invariants (not just app checks).
- Production migrations run as the owner role (`MIGRATE_DATABASE_URL`); the runtime role only gets DML grants via default privileges.
- Back up before applying to production (`scripts/backup/backup.sh`).
